## 0. 结论先行

**一句话：这个项目的问题不是「死代码太多」，而是「活代码太多，而且每块活代码都以为自己是大脑」。**

1. **可直接删除的已证死代码很少。** 全仓静态扫描能确认「无任何调用方、无测试、无配置启用」的只有 `maybe_auto_fibi()`、`_pp_actor()` 两个函数（约 60 行）和 `napcat.compose_dir` 一个配置键。把清理等同于删代码，会删错地方。
2. **真正的臃肿在决策层和状态层。** 19,636 行的 `bot.py` 里，626 个函数、288 个模块级状态、181 条 `re.compile`；一条消息进模型之前要过 **15 个 `_route_*` + 3 个内联分支**；模型有 **6 条入口路径**；能力有 **3 套工具面**；记忆/状态有 **9 套 + 3 套图片缓存**；Prompt 有 **18 段**各自追加。
3. **「画这两个 / 画上面那两幅画」到今天仍然会错。** 上一轮只修了 Moss Studio 路径，没有修这个。现在已定位到完整链路：`_BARE_DRAW_RE` 不认复数指代；`parse_draw()` 对中文宽松句会返回 `None`；于是消息落到 `_route_ai_draw`，主大脑只看到文字，把「这两个」当成合法描述直接开画；若指令是配在图片上发的，则被 `_route_private_recall_vqa` 当成看图提问。并且全项目所有视觉/画图链路只取 `imgs[0]`，**第二张图在类型层面就不存在**；30 分钟图片记忆 `_vg_assets` 只给视频和看图回捞用，画图链路从不读取它。这不是补一个词能解决的。（逐行证据见 §4.3①）
4. **目标架构不是再加模块，而是「收回决定权、统一状态、保留能力」。** 现有能力模块（ComfyUI/Moss/反推/视频/翻唱/JM/meme/捏脸/混淆/语音/技能/梗库）几乎都保留；要退役的是**用自然语言正则替用户决定意图**的那一层，以及同一事实的多份真相。
5. **本轮结束后应停在这里。** 报告给出逐项裁决、目标架构、统一数据流和 M0–M6 迁移路线；不开始 M1，不改代码。

### 0.2 日志证据的边界

`bot.log` 覆盖 2026-10-25 → 11-05，88,395 行、20,678 条消息。**其中包含自动化测试经真实 QQ 发出的重复消息**（例如 `/status` 出现 341 次、「设置 画图档 krea2」278 次）。因此：

- 原始计数只能说明「这条链路在跑」，不能说明「用户在用」；

1. **静态**：`ast` 解析全部根模块；统计函数、模块级状态、正则、线程、异常；对每个模块做 importer 反查；对 `bot.py` 每个顶层函数做全仓引用计数；抽取 `KNOBS` 230 项与 `config.json` 514 个叶子键做双向比对。
2. **动态**：读取 11 天 `bot.log` 统计链路命中；读取 `state/maimem.db`、`metrics.db`、`memory-card.json`、`purpose.json`、`mood.json` 等真实数据规模；核对 `.bat/.vbs/.ps1`、`state/agent-mcp.json`、`HANDOVER.md` 中的外部调用方。
3. **交叉**：每个「未使用」判断至少经过「import 反查 + 调用点扫描 + 测试引用 + 配置启用 + 日志痕迹 + 外部脚本」六项中的三项，才敢下 REMOVE；不足的进 DEFER。

### 1.2 证据等级

| 等级 | 含义 | 用法 |

| A | 代码调用链 + 测试 + 运行日志/状态数据三方一致 | 可直接裁决 |

### 2.5 当前架构为什么必然「有工具、没理解」

1. **意图在模型之前就被决定。** 181 条正则中，真正属于「安全/权限/不可逆/显式协议」的不到 20 条；其余把自然语言当命令解析。
2. **媒体不是一等公民。** 图只在当前这一轮以 base64 塞进 messages；`HISTORY` 只存文本；引用图靠 `quoted_images(qmid)` 临时取；所有画图/反推入口只取 `imgs[0]`（10 处，见 §5.2）。模型无法知道「上一轮那两张图」是什么，因为它从来没拿到过。
3. **状态各写各的。** 同一轮对话被写进 HISTORY、turns、memory-card、reflect、slang、expression、mood 七个地方，各自的截断/衰减/隔离规则不同。
4. **工具只是「最后的手段」。** 正则能认领的动作，模型永远看不到；模型看到的只剩无法口令化的闲聊，自然显得不会用工具。
5. **人格只在最后一段生效。** 角色卡进 system 开头，但意图、工具、拒答、发图、回复长度在到达 system 之前已被 18 个分支决定。

## 4. 意图判断权专项审计

### 4.1 判定原则（本轮采用的唯一标准）

一条消息在**模型理解之前**被代码决定去做什么，只有四种情况允许：

1. **安全**：违禁词、骚扰硬闸、出站密钥审计。
2. **权限**：管理员命令、仅主人、群白名单。
3. **不可逆/危险操作**：写配置、删文件、跑命令、发到别的会话。
4. **显式协议命令**：有独立命名空间、写法固定、可被文档枚举，例如 `/status`、`/help`、`.jm <id>`。

除此之外，**业务意图一律不得由关键词/正则抢先决定**。速度问题应该在新核心内部用「高置信度快路径」解决，而不是在核心之前设卡。

### 4.3 已能复现的误判（本轮新确认，带代码证据）

**① 「画这两个」/「画上面那两幅画」仍然错（上一轮未修）**

实际有两条分叉，取决于指令是不是配在图片上发的：

- `_BARE_DRAW_RE`（`bot.py:2215`）只认 `这个/这张/这图/这幅/它/上面那张/刚才那张`，**不认「这两个」「那两幅」**，所以 `_bare_hit = False`。
- `parse_draw()`（`qbot_draw_body.py:1211`）里，`DRAW_LOOSE_RE` 虽然能匹配「画」+ 剩余文本，但宽松分支只在「成品 tag 串」或「纯英文」时才返回（`1261-1275`）；中文句 `looks_like_tagline()` 直接返回 False（`comfy_gen.py:803-804`）。所以 `parse_draw` 返回 `None`——**它既没认出这是画图，也没保留指代信息**。
- **情况 A：指令单独发（图在前两条消息）** → 本条 `pic_imgs` 为空 → `_route_ai_draw` 满足条件（`bot.py:15951`，要求 `not pic_imgs`）→ `_ai_route_draw` 只把文字交给主大脑（`qbot_draw_body.py:315-318`）→ 模型返回 `prompt="这两个"` → `_route_prompt_grounded()` 因为「这两个」是原话子串而放行（`qbot_draw_body.py:276-277`）→ `draw_submit("这两个")`。**于是画出来的是文字想象，不是那两张图。**
- **情况 B：指令配在图片上发** → `pic_imgs` 非空 → `_route_ai_draw` 被跳过 → `_route_moss_edit_pic` 不命中 → `_route_private_recall_vqa` 因 `pic_imgs and addressed and not placeholder_only(text)` 成立（`bot.py:16019`）把整轮交给 `sim_vqa_chat` → **它回答问题，而不画图**。
- 关键结构性事实：`_vg_assets` 里其实存着这个人 30 分钟内发的图（`bot.py:15109`），但**画图链路从不读它**——读它的只有视频生成、翻唱取视频、看图回捞（`15533/15811/15829/16013`）。再加上全项目 **10 处 `imgs[0]`**（`2535/3364/3407/3614/3895/10690/10865/15835/15932`），**「这两个」在类型上无法表达**。

**② 私聊「图书馆怎么走」被当成看图提问**

- `_route_private_recall_vqa`（`bot.py:16012`）条件是 `("图" in ins) or (_recent and _is_img_ref(ins))`。
- 只要 30 分钟内发过图，任何含「图」的私聊都会被回捞成 `pic_imgs`，随后进入 `sim_vqa_chat` 并 `return True`（`16022`）。
- 「图书馆怎么走」「地图发我」都会走视觉问答，而不是核心。

**③ 带图说「把这个加上」被当成改图**

- `_looks_like_edit` 命中「加上」，且 `_moss_only(gid)` 为真 → `handle_moss_edit`，`return True`。用户可能只是在说「把这个加到清单里」。
- 同理，「把图片发我」命中「发」类词、带图时也可能被抢。

**④ 配置关键词可以吞掉任意消息**

- `config.json` 的 `keywords` 支持 `mode: contains`。当前有一条「渲染完成」，任何包含这四个字的消息都会被替换成固定回复，模型永远看不到。

### 4.4 允许保留的硬轨（白名单，穷举）

1. 管理命令：`/status /reset /silent /active /role /roles /mute /unmute /welcome /help`。
2. 显式下载/系统命令：`.jm <id>`、`/moss_submit`（API）。
3. 安全：`ban_words`、`_bro_gate`、出站 `audit_ok`。
4. 不可逆操作：配置写、文件删除、命令执行（当前只在 agent 工具面）。
5. 传输层：重复 message_id 去重、自身消息忽略、群白名单。
6. 明确协议参数：`/画 <描述>` 这类**只作为工具调用的简写**，解析后立即调用同一工具，不参与「要不要画」的判断。

### 4.5 退役后如何不误伤

- 所有自然语言能力（画/反推/改图/翻唱/视频/捏脸/meme/混淆）在 M3 之后都已是**工具**；核心看到的是同一套 `ToolSpec`，不会因为正则删了就失去能力。
- 显式命令保留为「命令适配器 → 同一工具」，只是不再拥有「我是不是这个意图」的解释权。
- 用 golden set 锁行为：退役前把现有 150 条真实命令文本 + 5 个已知误判案例固化成用例，退役后必须全部通过（含「该画 / 该聊 / 该问」三分类）。

## 5. 僵尸路由、重复功能、失效代码（证据）

### 5.1 路由层的「僵尸」不是死代码，是**互相遮蔽**

15 个 `_route_*` 中，画图相关有 4 个（`draw_and_moss` / `bare_draw` / `ai_draw` / `moss_edit`），看图有 3 个（`pic_only` / `recall_vqa` / `see`），视频有 2 个（`video_cmds` / `link_and_keywords` 的链接）。它们不是没人用，而是**谁先匹配谁说话**：

- `_route_draw_and_moss_cmds` 的 `REVERSE_RE` 是句首「反推」即命中，日志里真人消息确实出现过「反推好了：…」这类叙述/复述句（`bot.log` 去重后仍在真人集合中），它会被当成命令而不是聊天。
- `_route_bare_draw_and_submit` 与 `_route_ai_draw` 是互斥的：前者一旦 `drawn` 为真，后者永远不执行；而 `drawn` 的判据是宽松正则。
- `_route_moss_edit_pic` 明确注释「必须排在所有口令之后、看图问答之前」——这个顺序本身就是设计债：**正确性依赖调用顺序**。

### 5.2 三套图片记忆，没有一套把「原图」交给核心

| 缓存 | 写入 | 读取 | 生命周期 | 问题 |
|---|---|---|---|---|
| `_msg_images` | 每条带图消息 | 引用取图 | LRU 内存 | 重启即失；只按 mid |
| `_vg_assets` | 每条带图/视频消息 | 视频/看图回捞 | 30 分钟 per (gid,uid) | 与 `_msg_images` 重复 |
| `_keep_seen` | 看图/omni 轮次 | 下一轮 Prompt | 写进 HISTORY | 只是文字转述，会丢细节 |

三者互不读取；`HISTORY` 里永远只有 `[图片]` 占位符，只有 `_keep_seen` 会把「模型自己当时怎么描述这张图」写成一段文字追进 HISTORY——细节已经在转述时丢了。**这就是「图片从未以原图进入会话上下文」的机制性原因。**

### 5.3 九套记忆/状态，同一事实多份真相

- `turns` 表 → 同时喂给 `facts`、`memory-card`、`reflect`；三者各自截断、各自衰减、各自注入。
- `memory-card` 220 条 vs `facts` 41 条 vs `reflect` 307 条：**同一段对话的三种摘要**，没有任何一份能回答「哪份是权威」。
- `person`/`fact` 与 `people`/`facts` 双表双写（`qbot_memory.py:572-648`）。
- `mood.json` 里存在 `[object Object]` 键（前端序列化 bug 留下的脏数据）。

| 层 | 默认 | 运行痕迹 | 与其它层的关系 |
|---|---|---|---|
| `sim` 合批插话 | 开 | 595 次实际插话 | 先过 mood/冷却/配额 |
| `sim.idle` 冷场开场 | 开 | 37 次「主动开场」 | 被 purpose 替代（若开） |

四层各自有状态文件、各自有测试、各自有配置段；实际生效的只有 sim + mood。这不是「渐进增强」，是**同一职责的四次实现**。

## 8. 目标架构

### 8.1 一张图

```
                        ┌──────────────────────────────┐
NapCat 事件 ──► Adapter ─► Turn（文本/媒体/引用/会话/人）│
                        └──────────────┬───────────────┘
                                       ▼
                        ┌──────────────────────────────┐
                        │ Context Assembler            │
                        │  policy + persona + 最近轮次   │
                        │  + 记忆召回 + 媒体描述 + 技能   │
                        │  唯一允许拼 Prompt 的地方      │
                        └──────────────┬───────────────┘
                                       ▼
                        ┌──────────────────────────────┐
                        │ Agent Core（唯一决策循环）     │
                        │  理解 → 判断 → 决策 → 行动     │
                        │  → 观察结果 → 直到收尾/放弃    │
                        └───────┬──────────────┬───────┘
                                │              │
                    ┌───────────▼───┐   ┌──────▼────────────┐
                    │ Tool Registry │   │ Memory Service     │
                    │ 统一契约/权限  │   │ 统一读写/隔离/衰减  │
                    └───────┬───────┘   └──────┬────────────┘
                            │                  │
          ┌─────────────────▼──────────────────▼─────────────┐
          │ 能力实现：draw / reverse / video / cover / jm /   │
          │ meme / petpet / scramble / voice / search / qq    │
          └─────────────────┬────────────────────────────────┘
                            ▼
                    ┌───────────────┐
                    │ Renderer      │  人格只在这里生效
                    │ 分条/拟人/审计 │
                    └───────┬───────┘
                            ▼
                         发送 / 或 SILENT
                            │
                    ┌───────▼────────┐
                    │ Store.commit   │  本轮 → 事件日志（唯一真源）
                    └────────────────┘
```

### 8.2 六个部件的最小职责

| 部件 | 只做一件事 | 明确不做 |
|---|---|---|
| **Adapter** | OneBot 事件 → `Turn`；发送 → NapCat | 不判断意图、不拼 Prompt |
| **Context Assembler** | `Turn` → 模型消息 + 工具清单 + 预算 | 不调用工具、不发消息 |
| **Agent Core** | 决定「回/问/调工具/沉默」并循环 | 不直接发消息、不直接写库 |
| **Tool Registry** | 注册/校验/权限/超时/结果 | 不解释自然语言、不拼话术 |
| **Memory Service** | 召回/写入/隔离/衰减 | 不决定说什么 |
| **Renderer** | 意图 + 文本 + 人格 → 出站分段 | 不改变事实、不选工具 |

> 这不是「七个新模块」。`Adapter`、`Renderer` 是把现有发送/解析代码收拢；`Context Assembler` 是把 18 段拼接收拢；`Agent Core` 是把 6 条大脑路径收拢；`Tool Registry` 是把 3 套工具面收拢；`Memory Service` 是把 9 套存储收拢。**数量在减少，不是增加。**

### 8.3 四个数据契约（先定契约，再写实现）

**Turn**
```
Turn {
  id, session{kind,key}, actor{uid,name,role,is_owner},
  text, media[MediaRef], quote{text, media[]} | null,
  addressed, flags, at, reply_to
}
```
- 所有组件只读 `Turn`，不再各自解析原始事件、不再各自 `imgs[0]`。
- 图片、引用图、转发图、视频首帧都在 `Adapter` 阶段归一成 `MediaRef`。

**MediaRef**
```
MediaRef { id, kind(image/video/audio/file), local_path, source_url,
           hash, w,h,duration, origin(current/quote/forward/recall), ttl }
```
- `MediaStore.recent(session, actor, kind, ttl)` 取代 `_vg_assets` / `_msg_images`。
- `Turn.media` 与历史轮次的 `MediaRef` 一起进入 Context；模型第一次真正「看得见上一轮那两张图」。

**ToolSpec / ToolResult**
```
ToolSpec {
  name, description, input_schema,
  scope(public/owner/admin), side_effect(none/session/external/irreversible),
  timeout_sec, cost, idempotency, audit
}
ToolResult { ok, data, user_text?, artifacts[], error_code, retryable }
```
- 权限、超时、幂等、审计在 Registry 统一实现；handler 不再各自判权限。
- MCP、HTTP API、正则命令适配器全部从同一 Registry 生成。

**Memory 记录**
```
Evidence { id, scope, kind, text, source_turn, confidence, expires_at }
Scope { session_key, actor_id, persona_id }
```
- 只有事件日志是原始真源；facts / card / reflect / slang / expression 都是**投影**，可由事件重建。
- 召回统一返回 `Evidence[]`，带来源轮次，Prompt 里可引用。

### 8.4 人格如何作用于全过程

- **身份/语气/边界**进入每一轮的 system（Assembler），不是只影响最后一句。
- **表达风格**由 Renderer 执行：分条、语气词、长度、是否配图。
- **价值判断**（什么该拒绝、什么该沉默、什么该主动）作为 Persona 的 policy 段进入核心。
- 人格**不参与**工具选择与事实判断；同一人格换模型，行为不应变化。

### 8.5 如何防止未来再造一条独立路由

1. **架构测试**：`core/` 之外禁止 `send_group`/`send_bubbles`；`_handle_message` 之外禁止新增消息入口；工具必须注册 `ToolSpec`。
2. **PR 检查**：新增 `re.compile` 必须声明用途；若用于「判断用户想干什么」，CI 直接拒绝（白名单只允许安全/协议）。
3. **唯一出口**：所有用户可见文本必须经过 `Renderer`；任何 handler 直接发送视为失败。
4. **契约测试**：新增能力必须提供 `ToolSpec` + 权限矩阵 + 失败返回；没有 spec 的能力不可被核心调用。
5. **回归集**：golden set 每次迁移跑；新增误判案例先补进 golden set，再修。

## 9. 统一数据流设计

### 9.1 一条消息如何携带文本 / 图片 / 引用 / 历史 / 任务状态

```
事件
 ├─ text                  → Turn.text
 ├─ image/video/audio 段  → MediaStore.ingest → Turn.media[MediaRef]
 ├─ reply 段(qmid)        → 取被引用消息 → Turn.quote{text, media[]}
 ├─ 转发                   → 摊平为 quote/attachments（不再单独 remember_images）
 └─ sender/role/session   → Turn.actor / Turn.session
        │
        ▼
Context.build(turn)
 ├─ 最近 N 轮（每轮带 MediaRef，不只文本）
 ├─ 本轮 media（vision parts 或缩略描述）
 ├─ 引用（文本围栏 + 引用图 MediaRef）
 ├─ Memory.recall(scope, query, budget) → Evidence[]
 └─ persona / policy / skills / 时间
```

- **历史**：`TurnStore` 是唯一历史；`HISTORY` 的 deque 语义变成 `TurnStore.recent()` 的实现细节。
- **任务状态**：长任务（视频/翻唱/画图队列）作为 `TaskRef` 挂在 Turn 上；核心能看到「上一轮那个任务跑完没有」，而不是靠用户再问一次。
- **图片跨轮**：不再依赖 `note_image_seen` 的文字转述；能附图就附图，不能附图才用自动描述兜底。

### 9.2 记忆统一读写 / 隔离 / 注入

```
写：Core 结束一轮 → Memory.append(event) → 投影异步更新（facts/card/reflect）
读：Context.build → Memory.recall(scope, query, k, budget) → Evidence[]
隔离：Scope(session_key, actor_id, persona_id)
      private 记录永不进 group；群记录按群隔离；人格按 persona 隔离
衰减：投影各自定义，但都从事件日志可重建
```

- 取消 `memory-card` 自己从 `turns` 再导一份的写入；它变成 `facts` 的一个视图。
- `reflect` 只作为「待验证结论」投影，不直接进入 Prompt 的权威事实。
- 召回带 `source_turn`，模型可以说「你上次说过…」并可追溯。

### 9.3 工具统一注册 / 调用 / 返回

```
Registry.register(spec, impl)
Core: tool_call(name, args) 
  → Registry.validate(spec, args, ctx)      # 参数/权限/预算
  → impl(ctx, **args)                        # 纯能力，不拼话术
  → ToolResult                               # 统一结构
  → Core.observe(result)                     # 继续循环或收尾
```

- `draw` 工具接收 `MediaRef[]`，内部决定用第几张、是否多图参考；核心不再关心 `imgs[0]`。
- `reverse` / `edit` / `video` 同样接收 `Turn` 的媒体集合。
- 正则命令适配器只负责把 `/画 一只猫` 解析成 `draw(what="一只猫")`，不参与「这是不是画图」的判断。

### 9.4 上下文注入预算

Assembler 给每类来源固定预算（可配置）：

| 来源 | 预算 | 优先级 |
|---|---:|---:|
| BASE_RULES + persona | 固定 | 最高 |
| 本轮 Turn（文本 + 媒体） | 固定 | 最高 |
| 引用 | 上限 12k 字 | 高 |
| 最近轮次 | 12 条 / 按 token 截断 | 高 |
| 记忆召回 | 4 条 / 320 字 | 中 |
| 记忆卡 | 1,200 字 | 中 |
| 技能 / 梗库 / 链接 | 各自上限 | 低 |
| 黑话 / 表达 / 心情 | 小段 | 低 |

超出预算时按优先级丢弃，并在日志记录「丢了什么」——不再像现在这样各模块无上限追加。

### 9.5 出站渲染

```
Core 产出 ReplyIntent { text, emotion, attach[], silent? }
  → Renderer: 角色语气 / 分条 / 拟人停顿 / 语音 / 配图
  → Policy: 密钥/路径审计、长度、频率、静默
  → Sender: NapCat
```

人格只在这一层改变「怎么说」，不改变「说什么/做不做」。

## 10. 七个问题逐条回答

**Q1：一条用户消息如何同时携带文本、图片、引用、历史、任务状态？**
`Turn` 是唯一载体：`text`、`media[MediaRef]`、`quote{text,media}`、`session/actor`、`task_refs`。历史是 `TurnStore` 里的 `Turn[]`，每轮都带媒体引用；任务状态是挂在 Turn 上的 `TaskRef`。任何组件都不再直接读原始 OneBot 事件。

**Q2：谁理解用户的真实意图？**
Agent Core。它拿到的是完整 Turn + 上下文 + 工具清单；正则只保留安全/权限/协议四类硬轨，不再解释业务意图。核心可以在不确定时**提问**，而不是猜一个工具。

**Q3：谁决定聊天、提问、调工具、拒绝、沉默？**
同一个 Agent Core。输出是 `Action[]`：`reply` / `ask` / `tool_call` / `refuse` / `silent`。拒绝与沉默由 Persona policy + 安全策略约束，但决定权在核心。

**Q4：工具如何统一注册、调用、返回？**
`ToolSpec` + `ToolResult` 契约；Registry 统一做参数校验、权限、超时、幂等、审计；MCP/HTTP/命令适配器都从 Registry 生成。能力实现只做一件事，不拼话术、不判权限。

**Q5：记忆如何统一读写、隔离、注入？**
事件日志是唯一真源；facts/card/reflect/slang/expression 是投影；`Memory.recall(scope, query, budget)` 统一返回带来源的 `Evidence[]`；`Scope(session, actor, persona)` 在服务层强制隔离，私聊永不进群。

**Q6：人格如何影响整个交互，而不只是最后一句话？**
Persona 分成三段：身份/边界（进每轮 system）、价值策略（进核心 policy）、表达风格（进 Renderer）。它不参与事实与工具选择，因此换模型不换人格。

**Q7：如何防止未来加功能又长出一条独立路由/状态链？**
架构测试 + 唯一出口 + ToolSpec 强制 + golden set。新增能力只能注册工具；新增状态只能进 Memory 投影；新增用户可见文本只能走 Renderer。违反即测试失败。

## 11. 迁移计划（M0–M6）

> 每个阶段独立 commit、推送私有远端、有验收证据、有回滚开关。**本轮不执行任何一步。**

### M0 基线冻结与 golden set

- **目标**：把「现在什么样」变成可回归的资产。
- **文件范围**：`tests/golden/`（新增）、`docs/reports/`（记录基线）。生产代码零改动。
- **内容**：从 6,844 条真人消息中脱敏抽取 200 条；标注「意图 / 应调工具 / 禁止动作」；必须包含：
  - 「画这两个」「画上面那两幅画」→ 应引用上一轮两张图；
  - 「生成一份报告」→ 应聊天，不应画图；
  - 「图书馆怎么走」（30 分钟内发过图）→ 应聊天；
  - 「把这个加上」（带图）→ 应询问或聊天，不应改图；
  - 「反推好了：…」→ 不应触发反推。
- **测试**：现有 SAFE 63/63；golden harness 只记录、不发送。
- **风险**：样本偏差。缓解：正负例各半，误判案例全覆盖。
- **提交**：`test: 架构迁移基线 golden set（只读）`
