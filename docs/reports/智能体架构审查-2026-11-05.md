## 0. 结论先行

**现在的 bot 不是"一个智能体"，而是"一个消息分类器 + 一个兜底 LLM"。**

一条消息进来，先被 15 个路由函数、大量画图/口令正则逐层"认领"；大脑排在最后，只处理前 14 层都没要的残余（[bot.py:18257](../../bot.py) `_handle_message` 239 行、[bot.py:18208](../../bot.py) `_route_brain_reply`）。所以它"有工具、没理解"不是模型笨，而是**结构上就没给模型理解的机会**。

15:05 那次"画上面那两幅画"是最干净的证据：

```
15:05:23 私聊: 画上面那两幅画          img=0 qmid=0
15:05:23 现画受理 ... what=上面那两幅画   ← 直接进画图，模型从未拿到那两张图
```

两张图是前一条/前几条消息发的，既不在本轮 `Turn` 里，也不在 `HISTORY` 里（历史只存文本），更不在任何"视觉上下文"里。系统把"上面那两幅画"当成**画面描述**交给 Moss，于是画出了一面墙和两幅装饰画——它忠实地画了字面意思，因为那是它唯一拿到的东西。

**这不是"再加一个图片理解模块"能解决的。** 需要改的是数据流方向：让"一条消息 + 它的图 + 它的引用 + 最近的对话 + 当前任务"先合成一个模型可理解的整体，再让同一个核心决定"回话 / 调工具 / 追问 / 沉默"。这正是主人说的"统一智能核心"。

### 2.4 上下文组装（`build_messages`，`qbot_persona.py:284`）

system 字符串按顺序拼接：

```
BASE_RULES（铁律） → 当前时间 → 角色卡正文 → extra[]（宿主传）
→ 黑话 → 语境释义 → 表达习惯 → 群最近对话 → 心情 → 引用资料围栏
→ [HISTORY 尾巴原样追加到 messages]
```

`ai_reply` 在调用前又往 `extra` 里塞了：记忆三段（`_memory_ctx_blocks`，`bot.py:19527`）、身份段、技能包提示词、链接速览、梗百科预查；`brain_with_tools` 再追加：总控系统提示、防注入规则、身份段、**本轮图片状态文字**（`bot.py:6393`）。合计 **12+ 个独立注入点**，各自有自己的开关、预算和失败降级。

`HISTORY` 是 `deque[dict(role,content)]`，**只有文本**；图片只在当前轮以 OpenAI vision parts 进入一次（`bot.py:6414-6430`），下一轮就只剩 `_keep_seen` 写的一条文字摘要（`bot.py:2042`）。

## 3. 五个根本问题

### Q1：智能核心到底在哪里？

**不存在。** "智能"被判散在：

- 15 个路由函数（`_handle_message` 里 15 次 `if _route_xxx(): return`）
- 画图/口令正则与变体（粗计约 275 处 `DRAW|_RE` 匹配，含定义与引用，不是独立正则数）
- 6 条大脑路径（§2.3），按 config + 每条消息的条件临时选择
- 12+ 个 prompt 注入块（§2.4）
- 9 个状态存储（HISTORY、context、maimem.db、memory-card.json、reflect 表、purpose.json、slang.json、expression、mood.json）

没有任何一个地方同时掌握：这句话是什么、上一张图是什么、这个人在问什么、我现在能不能做、做完结果是什么。**每个局部都知道一点，没有一个整体知道全部。**

### Q2：上下文到底由谁负责？

**没有人负责。** 每个功能自己往 system 里拼一段，拼完就结束：

| 模态 | 现在怎么进模型 | 结构缺陷 |
|---|---|---|
| 当前文字 | `build_messages` 追加 user | 可以 |
| 本轮图片 | `brain_with_tools` 把图编码进 user parts | **只活一轮**，下一轮丢失 |
| 引用文字 | 包进 `【引用资料开始】` 围栏 | 只是字符串，不是结构化引用 |
| 引用图片 | `quoted_images(qmid)` 现取 | 只在部分链路接（§2.2 的 8/10/13/14） |
| 前几条消息的图 | `remember_images(mid)` 按 mid 存、`_vg_assets` 按人存 | **两套都不给画图/聊天用** |
| 历史对话 | `HISTORY` 纯文本 deque | 无图、无工具结果、无任务状态 |
| 长期记忆 | 4 段独立注入 | 无统一预算/冲突消解/相关性门槛 |
| 任务状态 | 无 | 画图队列/视频任务在各自模块里，模型看不见 |

结果就是主人看到的："我前面发了两张图，它一股脑画我说的文本。" **不是它不想看，是那两张图从来没进它的输入。**

### Q3：记忆为什么存在？是否有多套系统重复解决同一问题？

**有四套，而且各自为政。** 它们解决的不是同一个问题，但都没有统一的读写入口：

| 存储 | 位置 | 负责什么 | 注入方式 |
|---|---|---|---|
| `HISTORY` | 内存 deque | 当前会话最近 N 轮对话 | 原样追加为 messages |
| `context_block` | 内存 CONTEXT | 群最近聊天（带发言人） | 拼进 system |
| `qbot_memory`（facts/turns/people） | `state/maimem.db` | 人物画像、跨场合对话流、按句召回 | `_memory_ctx_blocks` 三段 |
| `qbot_memory_card` | `state/memory-card.json` | 叙事化长期记忆、衰减/复习/压缩 | 再拼一段 |
| `qbot_reflect` | maimem.db 的 reflect 表 | 观察/看法/未完成事项 | 不进 prompt（只入库） |
| `qbot_purpose` | `state/purpose.json` | 主动开口的 goal 池 | 只给主动链路 |
| `qbot_slang` / `expression` | `state/*.json` | 黑话/表达习惯 | 拼进 system |
| `qbot_mood` | `state/mood.json` | 情绪状态 | 拼进 system |
| `_keep_seen` | HISTORY 里的一条文本 | "我看过的图长什么样" | 追加历史 |

**真正的问题不是"记忆太多"，而是没有"记忆服务"这个统一层**：谁都能写、谁都能读、谁都能决定注入什么，于是同一件事有多个近似实现（人物画像 vs 记忆卡 vs 反思），同一张图有 `remember_images` / `_vg_assets` / `_keep_seen` 三条记忆。

### Q4：工具为什么需要这么多特殊处理？

因为**工具不是契约，是 if/elif**：

- **三套工具面**：正则口令（15 个路由内的各种 `handle_*`）、`_BOT_TOOLS` 9 个进程内工具（`bot.py:5677`）、`qq-mcp-server.py` 20 个 MCP 工具（给 DSH/agent）。同一能力（画图/记忆/表情）在三套里各有一份参数解析和话术。
- **每个工具一套专用闸门**：`_draw_done` / `_rev_done` / 连续失败计数 / 同参去重 / 工具预算（`chat_once_tools`，`bot.py:6083-6169`）。这些不是通用策略，是六个工具各自的特例。
- **参数靠正则猜**：`parse_draw` 识别画风/图生图/宫格/长宽比/否定词；`meme` 用关键词表；`video` 用另一套。模型没有"函数签名"可依据。
- **结果话术各自写**：画图排队话术、meme 失败话术、Moss 反推失败话术、工具预算用尽话术……人格插不进去。

于是"工具越多，特例越多；特例越多，越不敢让模型自由调用"，最后只能继续加正则。

### Q5：人格为什么和智能分离？

因为人格只是 system 字符串里的一段正文（`qbot_persona.py:309-321`），它影响"怎么说话"，不影响：

- **要不要说话**（路由/静默/时机）
- **用什么工具**（正则/工具循环）
- **工具怎么调用**（参数由代码解析）
- **失败了怎么说**（各链路自己写死话术，`_draw_err_hint` 等）

所以一个有几万字人设、情绪状态机、黑话库的 bot，会回"画「上面那两幅画」，走云端 Moss，大概 15~30 秒"——**这句是系统话术，不是人格在说话**。人格和能力是两条平行管线，只在最后发送前碰一下。

## 4. 真实瓶颈（证据）

### 4.1 结构性证据

| 指标 | 实测 | 含义 |
|---|---|---|
| `_handle_message` 前置路由 | **15 层**，顺序执行、命中即 return | 大脑只处理残余 |
| 画图/口令正则 | **约 275 处** `DRAW|_RE` 匹配（粗计） | 意图判断靠字符串 |
| 大脑路径 | **6 条**（§2.3） | 行为随 provider 漂移 |

| prompt 注入块 | **12+**，4 个 `extra` 追加点 + 4 处 `sys_txt +=` | 上下文无人统一负责 |
| 记忆存储 | **9 处**（§Q3） | 无统一读写/预算 |
| 全局可变状态 | **约 21 个模块级 dict**、44 处 `threading.Thread` | 状态散落、时序靠约定 |
| 静默吞异常 | **50 处** `except: pass` | 故障不可见 |

### 4.2 事故证据（2026-11-05）

```
14:39:25 私聊: 画这两个            img=0
14:39:25 现画受理 what=这两个        ← 直接把"这两个"当提示词
14:39:27 现画失败: 提示词这步没成（布局与翻译都失败）   ← 当时旧 Studio 路径

15:05:23 私聊: 画上面那两幅画       img=0 qmid=0
15:05:23 现画受理 what=上面那两幅画  ← 两张图不在任何可见上下文
15:05:23 Studio 语言档 404 …        ← 配置漂移（另一层问题）
15:0x     画好了（37s, 1024x1824）   ← 画成了墙上的两幅装饰画
```

两层故障叠加：**路径/模型配置漂移**（可修，已修路径）+ **图片从未进入说话人的上下文**（结构问题，修不了单点）。即使把路径修好，15:05 仍然会画错——它拿到的是"上面那两幅画"六个字。

### 4.3 用户观察到的其它症状（来自 11-02 观察报告/真实日志）

- 工具选择 68%、工具风暴 46%（单条最多 12 次搜索）——工具没有统一契约，模型只能试错。
- 无图反推 17 次失败——模型不知道"这一轮有没有图"，只能猜。
- 群里问"今天几号"答不出——时间信息是后补进 system 的。
- 引用图片"隔一句就不认账"——图片只活一轮，下轮只剩文字摘要。

这些症状被逐个打补丁（工具预算、图片状态文字、时间行、`_keep_seen`……），每一个都是合理的局部修复，但**它们共同证明核心缺失**：没有统一上下文，就只能靠系统提示反复"告诉"模型事实。

## 5. 为什么会出现"有工具、没理解"

用一句话概括：**工具是代码的能力，理解是模型的能力；现在的架构只在"代码没认出来"的时候才把控制权交给模型。**

具体机制：

1. **先分类、后理解**：消息先被正则归到某个功能槽，模型只在槽外才被咨询。而语言的意义恰恰在槽的边界上（"画这两个"到底是画图指令还是指代前文？）。
2. **上下文是"补给"不是"输入"**：所有上下文都是事后拼进 system 的文字；模型没有结构化的会话状态可操作。
3. **工具是"命令"不是"动作"**：工具调用被写死参数解析，模型不能组合、追问、停止、改参数。
4. **人格是"滤镜"不是"决策者"**：人格不参与判断，只能给系统话术加语气。
5. **每加一个能力就多一层路由**：能力增长 → 正则增长 → 冲突增长 → 再加一层消歧。这是复杂度线性、智能不增长的根源。

## 6. 过去增加的模块：提高了智能，还是只增加了复杂度？

裁决口径：**是否让模型在"理解/判断/行动/修正"四件事上多了一点自主权**。不按开发成本、不按代码量。

| 模块 | 智能增量 | 复杂度增量 | 裁决 | 理由 |
|---|---|---|---|---|
| `qbot_memory`（facts/turns/people） | 中：按句召回、跨会话事实 | 中：3 段注入 + 多套检索参数 | **保留为存储/检索后端**，注入收口 | 数据有价值，注入方式重复 |
| `qbot_memory_card` | 中高：叙事记忆/遗忘曲线 | 中：又一段注入、又一套衰减 | **保留后端，合并注入** | 与 facts 解决不同层（叙事 vs 检索） |
| `qbot_reflect` | 中：可验证的观察 | 低：只入库不注入 | **保留为回合后反思** | 不参与开口，适合放进反思阶段 |
| `qbot_purpose` | 中：目标驱动主动开口 | 中：独立调度/独立生成路径 | **保留为目标源，接入统一循环** | 默认关，价值待验证；不应有独立发言管线 |
| `qbot_timing` | 中：时机门 | 低 | **保留为触发策略** | 适合做核心的 trigger policy |
| `qbot_mood` | 中：情绪连续性 | 低 | **保留为状态提供者** | 注入方式统一即可 |
| `qbot_slang` / `expression` | 低中：群文化 | 中：两段常驻注入 | **保留为按需上下文** | 不必每轮全量注入，相关性门槛 |
| `qbot_persona` | 高：人格表达 | 低 | **保留并升级为 Renderer** | 人格应参与"怎么说"，不参与"做什么" |
| `qbot_skills` / `skill_tools` | 中：技能包 | 高：提示词注入 + 4 域工具混装 | **合并进工具注册表** | 技能=工具+描述，不应是第三套工具面 |
| `qbot_memewiki` | 中：梗知识 | 中：预查注入 + 工具 | **保留工具，预查降级为工具** | 预查是"替模型查"的补丁 |
| `qbot_linkprev` | 中：链接内容 | 低 | **保留为上下文提供者/工具** | 模型有工具后可自己取，预抓可留作加速 |
| `qbot_meme` / `petpet` / `fibi` / `whale` / `trendy` | 中：表情能力 | 高：五条链路、三套口令、两套去重 | **合并为一个媒体工具面** | 同一意图五种实现 |
| `comfy_gen` / `moss_gen` / `moss_layout` / `reverser` | 高：真实出图能力 | 高但必要 | **保留为工具后端** | 这是真实能力，不是补丁 |
| `videoparse` / `tts` / `jm_bot` / `qbot_cover` | 中：媒体能力 | 中 | **保留为工具** | 链路独立、边界清楚 |
| `qbot_statuscard` | 低 | 低 | **保留为工具** | 单点能力 |
| `qbot_session` / `KNOBS` | 中：权限/策略 | 高：240 旋钮 | **保留为 Policy Store，瘦身** | 大多数旋钮应由核心判断 |
| `admin_html` / `webui` 双前端 | 无 | 高 | **按既有计划收口** | 与智能无关 |
| 15 个 `_route_*` | 低 | **高** | **合并为 2 层**（硬闸 + 核心分发） | 本报告核心裁决 |
| `parse_draw` / `_BARE_DRAW_RE` / `_ai_route_draw` / `_route_prompt_grounded` | 低（模型看得见图后不再需要） | 高 | **淘汰，能力迁入 draw 工具** | 275 处正则的主要来源 |
| `_task_intent` 正则 | 低 | 中 | **淘汰**（工具可见即可判断） | 词表永远漏 |
| 6 条大脑路径 | 中（外部 agent 有独特能力） | 高 | **收敛为 1 个 Adapter 接口，保留 DSH/agent 适配器** | 能力保留，分支消失 |

**总判断**：过去这些迭代加的功能**大多是真能力**（出图、视频、记忆、人格），但它们的**接入方式**是"每加一个能力就加一层路由/一段注入/一套话术"。所以智能没有线性增长，复杂度线性增长。重构要动的不是能力，是**接入方式**。

## 7. 目标架构：统一智能核心

### 7.1 关系图

```
                    ┌──────────────────────────────────────────┐
                    │              Policy Store                 │
                    │ 权限/白名单/额度/密钥/会话开关/安全审计    │
                    │（人设定政策，核心执行政策，不参与理解）    │
                    └───────────────┬──────────────────────────┘
                                    │ 只读
QQ → Transport/Identity → Turn ─────┼─────→ Context Assembler → Agent Core
      （保留：去重/白名单/审计）     │        （唯一上下文入口）      │
                                    │                               ├─ LLM Adapter（1 个接口）
                    ┌───────────────┴──────────┐                    │   ├─ API 模型
                    │        Memory Service    │                    │   ├─ DSH 适配器
                    │ working / episodic /     │←── 读写 ──────────┤   └─ agent 适配器
                    │ semantic / narrative /   │                    │
                    │ goals                    │                    ├─ Tool Registry（唯一能力面）
                    └──────────────────────────┘                    │   draw / search / meme /
                                                                    │   video / memory / admin…
                    ┌──────────────────────────┐                    │
                    │  Reflection & State      │←── 回合后写入 ─────┘
                    │ 结果/失败/目标/情绪/观察  │
                    └──────────────────────────┘
                                    │
                                    ▼
                          Renderer（人格声音）→ 发送层（保留）
```

### 7.2 七个部件（不是七个新功能模块，是七段职责）

| 部件 | 职责 | 关键约束 |
|---|---|---|
| **Transport/Identity** | 收事件、去重、白名单、审计、会话 key | 保持现状，零改动 |
| **Turn（新数据结构）** | 一条消息的完整语义：文本、图片引用、引用消息（文字+图）、发言人、触发类型、能力集 | 所有模态一等公民；图片带 TTL 的会话级视觉缓冲 |
| **Context Assembler** | 唯一决定"这轮模型看到什么"：分层 + 预算 + 优先级 | 每层声明 token 预算；禁止业务模块直接拼 system |
| **Agent Core** | 唯一决策循环：理解→判断→决策→行动→观察→反思 | 每轮只有它决定回话/调工具/追问/沉默 |
| **Tool Registry** | 唯一能力面：schema/权限/副作用/超时/成本/结果契约 | 业务代码不再写"这个口令怎么解析" |
| **Memory Service** | 唯一读写入口：working/episodic/semantic/narrative/goals | 存储后端可保留现有 SQLite/JSON |
| **Renderer** | 把"核心的决定 + 工具结果"用当前人格说出来 | 人格只影响表达，不影响权限/事实/工具选择 |

### 7.3 四个数据契约（先定契约，再谈实现）

```python
Turn = {
  "id", "session", "trigger",            # message | ambient | idle | event | admin
  "sender": {"uid","name","role","is_master"},
  "text", "parts",                        # parts 保留消息段原文
  "images": [{"ref","ts","source"}],      # 本条 + 会话视觉缓冲（最近 N 张，带时间）
  "quote": {"text", "images", "mid"},
  "capabilities": {...},                  # 本会话允许的工具/额度
}

ToolSpec = {
  "name", "description", "input_schema",
  "permission", "side_effect",            # none | exclusive | external
  "cost", "timeout", "result_schema",
}

ToolResult = {
  "ok", "data", "artifacts",              # 图/文件/链接
  "error": {"code","user_msg","retryable"},
  "effects": [...],                       # 已发生的真实副作用（发群/排队/写库）
}

ContextBudget = {                          # 组装器的唯一配置
  "layers": {"policy":∞, "persona":N, "turn":N,
             "working":N, "memory":N, "skills":N},
  "overflow": "drop_lowest_priority",
}
```

**"画这两个"在新架构里怎么走**：

1. Transport 产出 `Turn{text:"画这两个", images: 会话缓冲里最近两张图, ...}`
2. Assembler 把两张图作为 user message parts 放进本轮输入（不是文字摘要）
3. Core 看到图 + 文本，判断"用户指的是这两张图，要重画/参考"
4. 调 `draw_image{reference_images:[...], intent:"recreate"}`，或先追问"是照着这两张画吗"
5. 工具返回 `ToolResult{ok, artifacts}`；Renderer 用当前人格说"画好了，你看像不像"
6. 结果和失败原因写入 Reflection，下一轮仍可见

**没有任何一个"指代消解模块"**——模型看得见图，指代就是语言理解的一部分。

### 7.4 关于"路由"的边界（关键，防止新架构变成另一个神）

保留一层**硬闸**，且只做三件事：

1. **安全与身份**：白名单、去重、审计、权限（不可交给模型）。
2. **不可逆/高代价命令的确定性执行**：`/mute`、`/role`、`画图 启动`、`.jm` 等明确前缀。
3. **成本闸**：非 @ 的群闲聊可以先过一个便宜分类器决定"值不值得进核心"——**它只能决定"忽略"，不能决定"做什么"**。

除此之外，**所有意图判断交给核心**。这就是主人说的"不是关键词路由器，也不是固定工作流拼接器"。

### 7.5 主动性与反思

- 主动开口不再是独立生成管线：`purpose`/`timing`/`mood` 只产生 `Turn(trigger=idle|ambient)`，由**同一个 Core** 决定说不说、说什么、要不要用工具。
- 反思是 Core 的最后一个阶段（不是另一个会说话的模块）：把本轮结果、失败、用户反馈写回 Memory Service；下一轮由 Assembler 决定是否注入。
- 这样"主动性"和"聊天"共享同一个理解/判断核心，不会各长一套。

## 9. 兼容策略

1. **配置**：新增 `agent_core.*`（enabled/mode/domains/budget），旧键全部保留并由 legacy 路径读取；切换用 flag，不删键。`config.example.json` 同步。
2. **记忆数据**：不迁移、不改 schema；Memory Service 在现有 `maimem.db` / `memory-card.json` / `purpose.json` 上做统一读接口。旧注入路径可回退。
3. **工具实现**：`comfy_gen` / `moss_*` / `reverser` / `videoparse` / `tts` / `jm_bot` / `qbot_meme` / `qbot_petpet` 全部原样保留，只用 Registry 包一层；参数语义由 schema 固定，内部实现不动。
4. **人格**：`roles/*.md` 内容不改；Renderer 先复用现有 `build_messages` 的角色卡段，逐步把"表达规则"与"行为政策"拆开。
5. **外部接口**：`/api/*`、MCP、群口令、`/admin`/`/console` 全部不变；硬闸保留，所以管理命令行为零变化。
6. **测试**：现有 SAFE/MANUAL 全部保留；新增 shadow 差分测试与 golden set；旧路径在新路径稳定前必须保持全绿。

## 10. 版本保护与回滚

- **基线 tag**：`pre-agent-core-2026-11-05`（M0 打，推到私有远端）。
- **分支**：`agent-core` 从 master 切出；每阶段一个小 commit，阶段末推远端并打阶段 tag（`agent-core-m1` …）。
- **开关回滚**：所有新路径必须先有 `agent_core.mode=legacy|shadow|core`；出问题**改配置即回滚**，不用 revert 代码。

- **数据回滚**：本方案不改 schema、不删数据；只新增 Turn 缓冲（有 TTL、可清空）与 shadow 日志（`state/agent_core/`，可删）。

## 11. 明确不做的事

1. **不再新增"XX 理解模块"**（多模态上下文模块、意图理解模块、工具调度模块）——本方案用数据流解决，不加层。
2. **不推倒现有能力实现**：出图/视频/记忆/人格/安全全部保留。
3. **不在旧架构上继续加正则**：M1 之后冻结新的 `_route_*` 与口令正则。
4. **不追求一次性重写**：先影子、再单域、再全量；每步可回滚。
5. **不为了"看起来智能"而牺牲确定性**：安全、权限、不可逆操作仍走硬闸。

## 12. 待主人拍板的五个决定

1. **认不认这个方向**：统一智能核心（Turn + 单循环 + 工具契约 + 记忆服务），而不是继续加模块？
2. **M1 影子期多长**：建议 3~5 天真实流量（不改变行为），用 golden set 证明判断质量后再切。
3. **先切哪个域**：建议画图（当前痛点最集中、工具实现最完整、回滚最容易）。
4. **成本/延迟底线**：每条消息都进核心会增加 token 与 1~3 秒延迟；是否接受"非 @ 群闲聊先过便宜闸、@/私聊必进核心"？
5. **DSH/agent 的定位**：保留为 Adapter（独特能力：本地文件/命令/长任务），还是最终收敛掉？建议保留适配器、去掉分支。
