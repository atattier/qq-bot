# 别人怎么给 bot 加语音？——为什么他们不占显存，声音还鲜活

> 调研日期：2026-10-10 ｜ 目的：回答「为什么别人的 bot 加语音不占那么多内存，声音还很鲜活」
> 结论先行：**大多数 bot 压根不做本地 TTS。**「不占显存」和「鲜活」大概率是两条不同的路子凑出来的。

---

## 一、核心结论（先看这个）

| 问题 | 真相 |
|---|---|
| 为什么别人不占显存？ | **因为他们根本没跑本地模型。** 要么发预录音频文件，要么调云端 API（edge-tts / 腾讯内置 TTS）。 |
| 为什么别人的声音很鲜活？ | **因为那是真人录的，或者用了微软神经语音。** 本地小模型的自然度普遍不如这两者。 |
| 「不占显存」和「鲜活」能同时拿到吗？ | **能，但要换个思路——离线预生成。** 见第五节方案 A。 |

一句话：**「鲜活」的杠杆不在 TTS 引擎，在「声音来源」。**

---

## 二、别人的三条主流路线（按实际占比排序）

### 路线 1：预录语音包（最常见，也最"鲜活"）

bot 手里有一堆现成的 `.mp3` / `.silk`，按关键词或随机挑一条发出去。

- **典型形态**：口头禅、梗语音、"随机骂人""叫起床""晚安"之类的触发式语音。
- **为什么鲜活**：真人录的，有呼吸、有情绪、有瑕疵——**这是任何合成都模仿不来的**。
- **成本**：**0 显存、0 延迟**，就是读个文件。
- 早期 QQ bot 圈（go-cqhttp 时代）大量这么干，素材包满网飞。

### 路线 2：协议端内置 TTS（老牌做法）

```
[CQ:tts,text=要说的话]
```

- go-cqhttp / OneBot 协议**自带**的 TTS 段，实际走腾讯的语音服务。
- **零部署、零模型、零显存**，一行 CQ 码搞定。
- 缺点：音色固定（就那几个）、不能克隆、现在 NapCat 已不主推这个。

### 路线 3：edge-tts（当前最主流的"合成"方案）

- GitHub `rany2/edge-tts`，**12k+ stars**，被 5000+ 仓库依赖。
- 调微软 Edge 的云端神经语音，**免费无 key**，中文音色有晓晓/云希等几十个。
- **0 显存、0 本地模型**，实测 5.2s 音频约 3.3s 出。
- 微软神经网络语音自带语调起伏，比大多本地小模型自然。
- 缺点：**要联网，文本会上传到微软服务器**；不适合大规模商用。

> 我们 bot 目前已经在用这条做兜底，路子是对的。

|---|---|---|

## 四、为什么我们这个占了 2.26GB？（实测拆解）

实测显存增量 = 2265 − 373(空闲基线) = **1892 MB**。按模型文件体积拆解：

| 组件 | fp32 大小 | fp16 估计 |
|---|---|---|
| 中文 BERT（roberta-wwm-ext-large） | 621 MB | 311 MB |
| 中文 HuBERT | 180 MB | 90 MB |
| GPT（s1v3） | 148 MB | 74 MB |
| SoVITS（v2Pro） | 155 MB | 77 MB |
| 说话人验证 SV | 103 MB | 51 MB |
| **权重合计** | **1207 MB** | **603 MB** |

**结论：模型权重只占约 603MB，剩下的约 1289MB（68%）是 PyTorch CUDA context + 缓存分配器 + 激活值。**

⚠️ **这意味着：换个更小的模型，收益有限。** 只要还跑 PyTorch + CUDA，就有 1GB 量级的固定开销。
真正省显存的路径是：**① 不常驻 ② 跑 CPU ③ 用不带 CUDA 的推理栈（如 ONNX Runtime）**。

补充官方/社区给的降显存手段（我们都还没用）：
- `device: cpu`（零显存，但慢很多；官方实测 CPU RTF 0.526，需 16GB 内存）
- `is_half: false` 改 FP32（**反而更占**，别搞反；FP16 才是省一半）
- `parallel_infer: false`、`sample_steps` 调小、`batch_size=1`
- 用 `export_torch_script.py` 导出优化模型再推理

## 五、给我们的三条建议（按推荐度排序）

### 🥇 方案 A：离线预生成 + 语音包（**克隆声线 + 零常驻显存**）

**核心思路**：既然常驻贵，那就**别常驻**——把常用语句提前合成好存成文件，bot 发的时候只是读文件。

1. 需要时**临时启动** GPT-SoVITS，把一批常用回复（口头禅、问候、晚安、"好的""收到""我在"……）批量合成成 `.wav`；
2. 存进 `state/voice_pack/`，配一张「关键词/意图 → 音频文件」的映射表；
3. 服务关掉，显存归零；
4. bot 运行时：命中映射表 → **直接发预录文件**（0 显存 0 延迟）；没命中 → 走 edge-tts。

**好处**：
- 克隆的声线**照样用**，而且是**同一批、音色稳定**（零样本克隆每次都略有漂移，预生成反而更稳）；
- 运行时**0 显存、0 延迟**；
- 想最鲜活，可以自己录几句真人语音混进去。

### 🥈 方案 B：Kokoro-82M 常驻（≈0.5GB 显存，或纯 CPU）

- 82M 参数，中文 103 音色，Apache-2.0 可商用，ONNX 版 CPU 就能跑。
- 显存只要约 **0.5GB**（Q4_K_M 甚至 0.5GB 以内），比我们现在的 2.26GB **省 4 倍以上**。
- 代价：**不能克隆声线**，情绪表现一般。
- 适合：想要"本地、离线、便宜"，但不执着于"必须是某个人的声音"。

### 🥉 方案 C：维持现状（按需启动 GPT-SoVITS）

就是我们现在的做法。热态 1.4~2.3s 很快，代价是常驻 2.26GB。
适合：偶尔想玩克隆声线时手动开一下。

## 六、一句话决策表

| 你的诉求 | 选哪个 |
|---|---|
| 想省显存 + 要克隆声线 | **方案 A（离线预生成）** |
| 想省显存 + 不在乎声线是谁 | **方案 B（Kokoro-82M）** |
| 想最鲜活 + 不在乎克隆 | **预录真人语音包**（最鲜活，永远的第一名） |
| 就要"像我/像某个角色" | 方案 A 或 C（GPT-SoVITS） |
| 完全不想折腾 | edge-tts（现在已经在用） |
