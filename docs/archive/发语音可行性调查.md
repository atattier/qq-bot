# 给 bot 加「发语音」功能 —— 可行性调查

> 日期：2026-10-09 ｜ 结论先行：**可行，且通道已真机跑通**，零外部服务、零密钥、零新增依赖。

## 一、结论

| 问题 | 答案 | 依据 |
|---|---|---|
| NapCat 能发语音吗？ | **能** | `can_send_record` 返回 `{"yes": true}`（2026-10-09 实测） |
| 小鲸账号（123450002）有发语音权限吗？ | **有** | 同上，`yes:true` 就是账号侧权限判定 |
| 需要我先把音频转成 silk 吗？ | **不用**，NapCat 自动转 | 打包源码 `napcat.mjs` 的 `createValidSendPttElement()` → `pye()`：非 silk 会调 native ffmpeg `convertToNTSilkTct()` 转码再上传 |
| 转码靠什么？ | Windows 原生 addon `app/native/ffmpeg/ffmpegAddon.win32.x64.node` | 本机文件存在；不走外部 ffmpeg.exe（那条路 `convertToNTSilkTct` 未实现） |
| 语音从哪来？ | **`edge_tts` 已经装在 bot 的解释器里** | `<工具安装目录>/Python3.14.7` 实测 `import edge_tts` 成功 |
| 真机验证过了吗？ | **过了** | 直接调 NapCat 私聊发了一条 5.2s 中文语音，`status:ok / retcode:0 / message_id:1819305679` |

**一句话**：bot 只要在本地生成一个 mp3（edge-tts 3 秒就能出 5 秒语音），把**本地绝对路径**塞进 `{"type":"record","data":{"file":"<路径>"}}` 发给 NapCat，剩下的转码/上传/发送全自动。

## 二、已探明的技术链路

```
文字 ──edge-tts(免费,联网)──▶ mp3 ──┬─ NapCat record 段 ─▶ isSilk? ─否─▶ ffmpegAddon 转 silk ─┐
                                    └──────────────────────────────────────────────────────┤
                                                                             uploadFile(PTT)
                                                                                          │
                                                                                    QQ 语音条 ✅
```

- **record 段的 `file` 支持**（`napcat.mjs` 里 `OB11MessageRecord.data` = 通用 `FileBaseData`，与 image/video/file 同构）：
  本地绝对路径 ｜ `file:///` ｜ `http(s)://` URL ｜ `base64://` ｜ `data:`
  → 最省事的是**本地绝对路径**（不占内存、不额外上传）。
- **时长**：silk 直接读时长；非 silk 转完再读；读不到就按 `文件大小/1024/3` 秒估算。
- **调用点**：`createValidSendPttElement()` —— 转换失败抛 `语音转换失败, 请检查语音文件是否正常`，这就是将来排障的关键日志。

## 四、落地方案（建议）

新增 `tts.py`（纯标准库 + edge_tts），改动集中在三处：

1. **`tts.py`**：`synth(text, voice, out_path)` 封装（edge_tts 是 asyncio，用 `asyncio.run` 包成同步）；文本清洗（去 emoji/换行、限长度）；文件落 `state/tts/`；统一按时间戳命名。
2. **`bot.py` 发送层**：新增 `send_voice(cid, mp3_path, group_hint=None)` —— 复用现有 `_api_send()`（群/私聊自动分发 + 私聊假失败复核），消息段 = `[{"type":"record","data":{"file":<绝对路径>}}]`。**不改动任何既有发送路径**。
3. **触发入口 + 配置**：
   - 口令（示例）：「语音说 xxx」/「说给我听 xxx」/「用语音回」→ 走 TTS；
   - 配置块 `voice`：`enabled` / `voice` / `prefix` / `max_chars` / `cooldown_sec` / `max_per_hour` / `members_allowed` / `delete_after_send`；
   - `KNOBS` 注册（建议归入「对话」区，或新开「语音」区），权限默认 admin，热生效；
   - 队列：语音合成慢（3~5s），建议用一个**串行 worker**（照抄现画 `_draw_q` 模式），避免阻塞消息处理线程。

## 五、风险与限制

| 项 | 说明 |
|---|---|
| 语音时长上限 | QQ 语音条一般 ≤60s；实现时用 30~60s 实测确认（NapCat 侧无硬限制，是 QQ 服务端限制） |
| 风控 | 短时间大量语音消息比文字更易触发风控 → 必须带冷却 + 每小时上限（照抄现画那套闸） |
| 网络依赖 | edge-tts 要走微软服务；断网/被墙时降级为纯文字回复（不报错、静默回落） |
| 内容审计 | 现有 `audit_ok()` 只审文本；语音是二进制，**需在合成前对文本做同样的审计** |
| 隐私 | 语音会把文字念出来，内容是 bot 自己生成的，无额外泄露面 |
| 磁盘 | mp3 很小（5s≈31KB），发后删即可（`delete_after_send`） |
