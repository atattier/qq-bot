## A. 竞品研究

> 证据等级标注：【实截】= 本机 Chrome 实际渲染截图；【源码】= GitHub API/搜索到的仓库结构；【文档】= 官方文档抓取全文；【待验证】= 未能取证，只有二手信息。凡【待验证】不作为设计依据。

### A.1 AstrBot（Vue 3 + Naive UI）

证据：【文档】wiki「使用 WebUI」页全文（github.com/AstrBotDevs/AstrBot/wiki/zh-use-webui）；【源码】`dashboard/src/views/` 目录 19 个页面视图（经 GitHub API 实查）：Chat / Config / Console / Conversation / CronJob / Data / Extension / Persona / Platform / PluginView / Provider / SessionManagement / Settings / Trace / Welcome / Alkaid / SubAgent / About + 子目录（persona / stats / knowledge-base / authentication …）。

1. **侧边栏结构**（页面级，约 8-10 项）：对话 ChatUI / 模型提供商 / 配置文件 / 插件（含技能、MCP、管理行为）/ 数据与日志（统计·对话·日志·追踪四页签）/ 自定义规则 / 扩展功能 / 系统设置。侧边栏固定顺序，页面即能力域，不按「开关清单」组织。
2. **配置页三层结构**：顶部「配置文件选择器 + 搜索」固定；左侧**分区导航**固定（AI / 平台与消息 / 访问控制 / 插件 / 扩展功能，AI 下再分 模型/人格/能力/高级）；仅右侧内容滚动。分区数 ≤5，每区条目 ≤8。
3. **解决的管理问题**：①「配置漂移」——多配置文件（profile）+ 可视化/JSON 双模式 + 保存确认；②「找不到配置项」——顶部搜索跨分区定位；③「全局与业务混淆」——系统设置（常规/外观/网络/安全/维护/OpenAPI）独立于配置文件页。
4. **值得借鉴**：配置页「左分区导航 + 右内容滚动」的三层结构；配置项搜索；Trace/统计页作为运行监控的形态；插件页「已安装 / 市场」两页签 + 插件卡片进详情（可视化视图）。
5. **不适合我们**：多配置文件体系（我们单 config + 预设档已够）；知识库/MCP/子代理等页（我们无此业务）；800+ 插件的复杂市场（我们 6 个本地技能包）。
6. **迁移到我们**：三层配置结构 → 系统设置页；搜索 → 全局；Data/Trace 页形态 → 运行监控页；PersonaPage（AstrBot 有独立人格页）→ 人格中心。

### A.2 Koishi（Vue 3 + Naive UI）

证据：【文档】官方手册 extras.k.cyans.me/end-user/webui 与 koishi.js.org v3 文档（webui.html：默认路径 `/console`、状态页 `/status`、5 秒刷新配置）；【源码】@koishijs/plugin-console 架构（NodeConsole 服务端 + @koishijs/client 前端基座，`client` 目录源码结构 GitHub API 取证失败，**待验证**）；页面清单来自官方文档与搜索摘要。

1. **侧边栏**：仪表盘 / 插件市场（4000+，支持 `is:preview` 等过滤语法）/ 插件配置 / 沙盒（模拟聊天）/ 用户 / 计划任务 / 日志 / 依赖管理 / 数据库（Dataview）；**第三方插件用 `ctx.page()` 注册自己的侧边栏页**——插件即页面，控制台是壳。
2. **解决的管理问题**：①插件生态的统一管理（市场→安装→依赖→配置全链路）；②调试可视化（沙盒直接模拟对话）；③「运行状态」仪表盘化（/status 页 API + 5s 自动刷新）。
3. **值得借鉴**：「插件市场→依赖管理→配置」的安装链路完整性；沙盒页（对我们的价值：控制台里直接开一个模拟会话测人格，不动真群——**列为可选设计**，见 D.6）；侧边栏插件注册制（我们的技能包未来可挂自己的页）。
4. **不适合我们**：依赖管理/包管理器界面（我们无 npm 运行时）；多用户体系；4000+ 市场的复杂过滤。
5. **迁移到我们**：仪表盘自动刷新节奏（5s 级）→ 运行监控页；插件页签结构 → 插件与扩展页。

### A.3 Open WebUI（Svelte + Tailwind）

证据：【文档】docs.openwebui.com/llms.txt 索引实抓：`/features/administration`（analytics / banners / evaluation / interface-defaults / task-models / translations / webhooks 子页）+ `/features/authentication-access`（RBAC：roles/permissions/groups；认证：SSO/LDAP/SCIM/MFA/api-keys）；技术栈 Svelte+Tailwind 来自搜索结果【待验证——未读源码】。Admin Panel 入口「左下角用户名 → Admin Panel」、Users/Models 页签来自搜索结果与中文教程（含截图）【二手，标注待验证】。

1. **解决的管理问题**：①多用户权限（RBAC 三层：角色/权限/组）；②模型供给管理（Model Permissions 控谁能用什么模型）；③分析页（analytics：用量统计）。
2. **值得借鉴**：**分析页（analytics）作为一等页面**——消息量/活跃用户/模型用量趋势，正是我们 Dashboard 缺的；设置项按「管理面板设置 vs 用户个人设置」严格分层。
3. **不适合我们**：单主人单 bot，RBAC/SSO/MFA 全部过重；聊天界面不是我们控制台的职责（QQ 群才是聊天界面）。
4. **迁移到我们**：analytics 的图表形态（日/周切换、按模型/按会话排名）→ 运行监控页；「全局设置 vs 个人设置」分层思想 → 我们的「全局 vs 会话级」归属表（C.3）。

### A.4 Home Assistant（Lit Web Components）

证据：【实截】demo.home-assistant.io 本机 Chrome 实截（state/_ha_demo.png，1600×1000）；【源码】home-assistant/frontend 仓库 src/sidebar/（ha-sidebar）、src/panels/lovelace/ 位置来自搜索结果，仓库 API 取证失败【位置待验证，但组件行为已由实截证实】。

实截观察（这是四家里最值得抄的视觉骨架）：
1. **极窄图标侧栏（约 56-64px）**：默认只显示图标，hover/点击展开；顶部汉堡键可收成纯图标条——「导航占位最小化，内容占满」。
2. **Dashboard = 状态胶囊 + 卡片网格**：顶部横排关键状态胶囊（温度 10.5°C / 湿度 70.4% / 离家）；内容按**区域分组**（客厅/厨房/能源/空调/书房/室外/更新），每组一个小标题 + 2-4 列卡片；卡片内是「图标 + 名称 + 当前值 + 直接可操作的控件（滑条/开关）」——**状态与操作同卡**，不用进详情页。
3. 卡片内嵌**迷你趋势图**（Temperature 卡里一条 sparkline）——一屏内传达趋势，不跳页。
4. **解决的管理问题**：海量设备的「一眼看全、顺手就控」——对我们等价于：十几个能力域的「一眼看全、顺手就切」。
5. **迁移到我们**：磁贴墙的正确形态（状态+开关同卡+sparkline）；分组小标题的节奏感；窄图标侧栏。**不适合**：它的卡片堆是「设备控制」，我们不能照搬成堆 197 个开关——卡片必须是「域摘要+核心操作」，细节进二级。

### A.5 四家横向结论

| 维度 | 共性做法（我们的设计据此定） |
|---|---|
| 导航 | 页面级大项 ≤9；AstrBot/HA 把「配置」和「监控」**分成不同页面**而不是一页堆开关 |
| 层级 | 配置都是「分区导航 + 右侧内容」两层，无三层以上嵌套 |
| 找项 | AstrBot/Open WebUI 都有配置搜索——197 项规模下这是必需品不是装饰 |
| 监控 | Data(统计)/Trace(追踪)/analytics 都是独立一等页；数据以「趋势图 + 排名表」呈现 |
| 状态与操作 | HA 把状态和操作放进同一张卡；我们现状是「状态在概览卡、开关在另一页」——割裂 |
| 生态 | 插件页统一「已安装/市场」两页签 + 卡片详情（三家一致） |

### B.5 人格隔离现状（任务书要求的专项）

- 已有地基：`turns.persona` 列（qbot_memory.py:180-198，2026-10-26 加），Reflection 只处理「属于当前人格的 turns」，老记录 NULL 被跳过；`reflect_cursor` 按 (src, persona) 记游标（qbot_reflect.py:116）。
- **刻意的共享**：群友画像（people/facts）按 (gid, qq) 存、不按人格分——设计上人格共享「对这个群的人的了解」。这是合理语义（换人格不该失忆群友），但**控制台必须把「群友记忆」与「本人格的观点/反思」在 UI 上分成两个区块**，避免误解为泄漏。
- 缺口：无任何「按人格查看 reflect_item」的 API（现只有入库），人格中心的观点页需要新增只读端点。

### B.6 数据缺口汇总（Dashboard/监控页的前置依赖）
